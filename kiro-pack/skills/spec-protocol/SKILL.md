# spec-protocol: SPEC で進める

原典: Stira の運用メモ(SPEC 方式)。
使う場面: 3ファイル以上の変更、複数セッションにまたがる作業、ワーカーに分ける作業。

## 置き場所
対象リポジトリの `.kiro/specs/<機能名>/spec.md`(無ければ作る)。session_ledger の artifacts に spec のパスを入れる。

## 型
```
# <機能名>
## Requirements   何を・なぜ。受け入れ条件はチェック可能な文で
## Design         どう作るか、変更するファイル、テストで期待する結果
## Tasks          チェックボックス、最大2階層。各タスクは単独で検証できる大きさ
## Verify結果     全タスク後に記入
## 記録           問題・決定・テスト結果(日時つき)
```

## 進め方
1. Requirements と Design を書いたら、指揮官に見せて合意を取る(方針が明らかな小さい作業なら省略してよい)。
2. タスクを終えたら即チェックし、テスト結果を「記録」に書く。
3. 3タスクごとに8行以内で報告する(完了 / 成果物 / 未解決 / 次 / 質問)。
4. 問題が出たら、先に spec の「記録」に書いてから報告する。
5. セッションが切れたら、会話ではなく spec と ledger を読んで再開する。
6. 全タスク後に Verify: 受け入れ条件・Design・期待したテスト結果と実装を突き合わせる。検証はコードを読むだけで済ませず、結果(テスト出力・画面・スクリーンショット)を見る。可能なら文脈を持たないサブエージェントにやらせる。
7. 食い違いは「実装を直す」か「仕様を変える」かを指揮官に判断してもらう。

## 注意
- 1回に触るのは2〜3ファイルまで。大きな一括生成は途中で切れる。
- 既存ファイルの「更新」で全体を書き直さない。狙った箇所だけ編集する。
- 設計の「なぜ」は spec か docs に残す。AI の記憶にだけ置くと、人が説明できなくなる。
